# QA-30 A: independent financial baselines

`households.json` contains invented households, not user records. Amounts are CAD in the current engine's real-dollar frame; taxPeriod identifies the rules context even for cases with tax disabled. Each case separates `baselineRevision` (the application revision its input was composed against), `inputVersion` (the input schema), and `provenanceRef` (the hand-calculation ID or archived diagnostic probe). `expected` is hand-derived from the source formula recorded beside each case. The executable cases are intentionally small enough to check without calling another engine path to produce an expected number. Tests reject an active money tolerance above $0.01 even if JSON is edited.

`property-sales.json` activates P01 with its independently derived $100,000 sale proceeds. On the pre-fix baseline, the executable test failed at $140,000 (a $40,000 phantom principal payment); it now passes at $100,000 with no sale-year installment. `pending-audit.json` keeps corrected expectations and full diagnostic inputs for P02–P04, P10 and P17. Its `pendingFix` value names the implementation slice that must activate a failing reproduction together with its fix. These entries must never be treated as passing regression tests before activation. Do not copy the old diagnostic `observed*` fields into expected values. The original diagnostic script asserted the bug and is only provenance for the input; the expectation below comes from a cash identity, age calculation, or feasibility constraint. For P17 the independently provable claim is only that 70/70 fails at age 62: 50,000 TFSA less three years of 20,000 spending leaves a 10,000 gap, with no CPP/OAS or tax before age 70. Whether 61/65 or another path remains feasible through age 95 is pending an independent yearly cash/tax schedule. Additional P/T coverage is indexed in `audit-map.md`.

The current engine has no serializable opening/closing state or annual event ledger. `snapshot.test.ts` checks the safe, currently supported deterministic boundary and records the richer continuation contract as pending. `invariants.test.ts` includes a standalone reference ledger for a transfer, purchase and debt settlement, then applies the cash identity to a live no-tax projection. When BE-30/31 introduce production events, bind those event records to these reference amounts, rather than testing the reference ledger alone.

No new user feature or mode entry is introduced here. DM01/02/03/11 require actual guided and professional form completion and two-way switching. Storage preloads in existing E2E tests do not count. See `audit-map.md` for activation points.
