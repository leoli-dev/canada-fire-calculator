# QA-30 A: independent financial baselines

`households.json` contains invented households, not user records. Amounts are CAD in the current engine's real-dollar frame; taxPeriod identifies the rules context even for cases with tax disabled. `expected` is hand-derived from the source formula recorded beside each case. The executable cases are intentionally small enough to check without calling another engine path to produce an expected number. The tests use an absolute $0.01 tolerance.

`pending-audit.json` keeps corrected expectations and full diagnostic inputs for P01–P04, P10 and P17. Its `pendingFix` value names the implementation slice that must activate a failing reproduction together with its fix. These entries must never be treated as passing regression tests before activation. Do not copy the old diagnostic `observed*` fields into expected values. The original diagnostic script asserted the bug and is only provenance for the input; the expectation below comes from a cash identity, age calculation, or feasibility constraint. Additional P/T coverage is indexed in `audit-map.md`.

The current engine has no serializable opening/closing state or annual event ledger. `snapshot.test.ts` checks the safe, currently supported deterministic boundary and records the richer continuation contract as pending. `invariants.test.ts` includes a standalone reference ledger for a transfer, purchase and debt settlement, then applies the cash identity to a live no-tax projection. When BE-30/31 introduce production events, bind those event records to these reference amounts, rather than testing the reference ledger alone.

No new user feature or mode entry is introduced here. DM01/02/03/11 require actual guided and professional form completion and two-way switching. Storage preloads in existing E2E tests do not count. See `audit-map.md` for activation points.
